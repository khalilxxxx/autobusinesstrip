# MVP1.2 对话稳定性与工作流调整方案

日期：2026-09-09。性质：供审阅的调整方案，尚未修改 MVP1.1 节点或 Dify 应用。

## 1. 建议采用的方向

继续使用 Chatflow。本期完成四项调整：正常启动申请、一次自动修复、精简模型上下文、按当前缺口组织对话。业务校验、草稿合并、确认版本和模拟提交继续由代码控制。

本期保留现有增量操作结构，只增加 `START` 意图及修复所需的内部数据。将“事实提取与操作规划彻底分离”“复杂日期由独立解析模块处理”“跨轮恢复旧失败消息”“Agent 自主调用业务工具”列为下一阶段，分别用实测判断收益。

原因：现有日志已证明一个明确的失败入口；先增加恢复能力，可以用同一模型、相同用例直接比较效果。一次性替换整个理解结构和编排方式，会增加改造范围，也难以判断改善来自哪里。

### 本期范围

| 本期改动 | 要解决的问题 |
|---|---|
| 新增 `START`，无字段也能开始申请 | 用户只有提单意图时被拒绝 |
| N04 输出可修复类型，最多再解析一次 | 空增量、结构矛盾等直接结束对话 |
| 三条互斥路径汇成统一操作计划 | 修复成功后下游仍引用首次失败结果 |
| 精简 N02 提供给 N03 的草稿视图 | 历史证据、内部字段增加模型负担 |
| N09 按状态组织回复，保存追问目标 | 每轮展示大表和所有缺口，短回答缺少明确指向 |
| 增加真实模型对照验收 | 本地代码通过，但无法说明语义提取是否稳定 |

保持单人差旅 Demo、现有城市及交通候选、模拟提交的业务范围。活动、同行人等未实现要求仍须保留并阻止不完整提交。

## 2. 已确认的问题与验证边界

用户输入：

> 我明天要去出差了，帮我提个申请吧

用户提供的 N03 结构化输出为：

```json
{
  "intent": "UPDATE",
  "submit_requested": "N",
  "basic_updates": [],
  "trip_operations": [],
  "clarification": "",
  "consultation": "",
  "clarification_resolutions": []
}
```

N04 返回 `error_code=CONTRACT_INVALID`、`error_path=$`。现有 N04 在“UPDATE/NEW、无增量、无澄清”时主动返回失败，N05 随后进入 E01。

这份结构已用本地节点复现。将人工输出改为只新增一个含出发日期的行程、暂不填写目的地，则可以正常保存草稿。可确认：当前业务代码允许信息不完整；本次失败是 N03 漏提日期，叠加空增量直接拒绝。

上述检查没有调用公司模型，不能解释全部约 10% 异常，也不能给出改造后的准确率。日期示例统一采用**测试基准 2026-09-09、时区 Asia/Shanghai**，“明天”为 2026-09-10；这不是对原失败会话日期的推断。

## 3. 调整后的用户体验

| 场景 | 目标行为 |
|---|---|
| 空草稿：“帮我申请一下出差” | 初始化草稿，询问出发日期和目的地 |
| 空草稿：“我明天要去出差了，帮我提个申请吧” | 记录出发日期，询问目的地和具体业务目的 |
| 上轮询问目的地，本轮“上海” | 补充对应行程的目的地，保留已记录日期 |
| 上轮询问返程，本轮“周五回来” | 只补或改返程，保留去程及事由 |
| 多段行程：“日期改到下周” | 澄清哪一段、哪一天，允许继续补充其他明确内容 |
| “先别提交，我再看看” | 保留草稿，进入查看或引导，不创建单据 |
| 首次解析为空，修复成功 | 正常记录信息并继续提问；运行日志记录修复过程 |
| 首次和修复均不合格 | 明确提示本轮未记录，保留原草稿并提出具体问题 |
| 已有草稿：“帮我提个申请” | 继续当前草稿，不清空、不另建 |
| “事由改为拜访客户，确认提交” | 应用修改并展示新版确认单，等待对新版的独立确认 |

本次问题的预期回复示例：

> 好的，已记录出发日期为 9 月 10 日。这次去哪里，主要办什么事？

只有日期已经通过校验并保存，才能使用“已记录”。两次解析都失败时，不使用上述成功文案。

## 4. 工作流与节点调整

### 4.1 主路径

```text
N01 用户输入
  → N02 装载完整状态、生成精简模型上下文
  → N03 首次理解
  → N04 校验与错误分类
  → N05 按 status 选择一条路径
       ├─ OK       → N05P 传递有效计划
       ├─ REPAIR   → R01 修复 LLM → R02 再校验并生成最终计划
       │                         R01 调用失败 → R03 恢复提问计划
       └─ CLARIFY  → R03 恢复提问计划
  → N05G 聚合三条互斥路径的 plan_json
  → N05U 拆出 action 与 plan_json
  → N06 合并草稿
  → N07 业务校验
  → 原有交通建议分支 N07I/N07T/N07A/N07P/N07G
  → N08 提交或非提交分流
  → N09 回复与状态 / N10 模拟提交
  → N11 → N12 → N13 保存 → N14 回复
```

R02 的业务校验结果不合格时，直接生成 `action=CLARIFY` 的无修改计划，汇入 N05G；不再调用 R01。R02 自身代码执行异常仍走系统异常出口。

### 4.2 新增节点

| 节点 | 类型 | 输入与输出 | 职责 |
|---|---|---|---|
| N05P | Code | 输入 N04.plan_json；输出 plan_json | 只在 N05 的 OK 分支运行，传递有效计划 |
| R01 | LLM | 输入 N04.repair_input_json；输出 structured_output | 根据原话、上下文和错误做一次重新解析 |
| R02 | Code | 输入 R01.structured_output、N02.query/state_json/context_json、N04.repair_input_json；输出 plan_json | 复用与 N04 相同的校验规则；通过则输出操作计划，失败则输出恢复提问计划 |
| R03 | Code | 输入 N02.query/state_json/context_json、N04.repair_input_json；输出 plan_json | 对无需修复或修复调用失败的情况生成恢复提问计划 |
| N05G | 变量聚合器 | 聚合 N05P.plan_json、R02.plan_json、R03.plan_json；输出 output | 汇总本轮实际执行的唯一分支；关闭分组 |
| N05U | Code | 输入 N05G.output；输出 action、plan_json | 校验统一计划封装，并提供后续节点可绑定的 String 输出 |

新增六个节点。保留 E01 作为异常路由保护时，画布由 21 个节点变为 27 个；不将普通模型输出问题继续送往 E01。

N04 在所有正常返回中都生成 `repair_input_json`，即使不需要修复也返回一个合法 JSON String。R03 只依赖 N02/N04 这组共同上游，不能引用可能未运行的 R01 或 R02 输出。

统一 plan_json 保留现有 `action`、`event`、`query`、`message`，新增 `origin`（PRIMARY / REPAIRED / RECOVERY）、`recovery_request`（无恢复事项时为 `{}`）和 `diagnostics`。有效 action 为 UPDATE / REVIEW / SUBMIT / CANCEL / GUIDE / CLARIFY。CLARIFY 的 event 使用 UNKNOWN 意图、N 提交标记和空更新数组；任何失败候选操作只能留在诊断中。N05U 检查该约定后才向下游输出。

### 4.3 必须同步修改的绑定

| 位置 | 现有引用 | 改为 |
|---|---|---|
| N05 条件 | N04.status=OK，其余到 E01 | OK→N05P；REPAIR→R01；CLARIFY→R03；意外状态→E01 |
| N06.plan_json | N04.plan_json | N05U.plan_json |
| N08 提交判断 | N04.action | N05U.action |
| N09.plan_json | N04.plan_json | N05U.plan_json |
| N10.plan_json | N04.plan_json | N05U.plan_json |

不能直接把 N04.plan_json 放进 N05G：N04 在每轮都会执行，失败时也可能产生输出。用 N05P 将第一条路径变成与其他两条互斥的实际执行分支。

### 4.4 现有节点的职责变化

| 节点 | 调整 |
|---|---|
| N02 | 支持新版状态；精简 current_draft；提供当前追问目标；向 N04 增加 context_json 输入绑定 |
| N03 | 增加 START；明确稀疏信息也应抽取；首次与修复使用同一 Schema |
| N04 | 分类错误、判断可修复性、生成修复输入；通过后保留原有证据和操作约束 |
| N06 | 对有效 START 规范化后的 UPDATE 创建空草稿；CLARIFY 不应用任何失败候选内容；candidate_json 同时携带候选 dialogue 状态 |
| N07 | 原业务规则继续执行；将未解决的恢复事项计入不能提交的待处理项 |
| N09 | 分阶段回复；保存当前提问的目标；处理 CLARIFY 和恢复事项生命周期 |
| N10 | 增加恢复事项检查；有未处理修改时阻止新提交，仍保留原确认版本及防重复规则 |
| N12 | 检查新版状态结构、恢复标记与可提交状态的一致性 |
| E01 | 仅保留为意外路由保护，输出业务可读提示并保留状态 |
| E99 | 继续处理调用/代码/状态异常；新 Code 节点的执行异常也接入 |

N03 在供应商错误重试后仍失败，继续走 E99。本期不增加入口前的纯命令旁路，因此“确认提交”等指令仍受 N03 节点可用性影响；可作为后续独立优化。

## 5. N03 的理解契约

### 5.1 新增 START，保留已有七个顶层字段

`START` 仅表示开始或继续填写申请，且本轮没有可提取的业务字段。包含日期、城市、具体事由或交通等事实时，应输出 UPDATE 和相应增量。

```json
{
  "intent": "START",
  "submit_requested": "N",
  "basic_updates": [],
  "trip_operations": [],
  "clarification": "",
  "consultation": "",
  "clarification_resolutions": []
}
```

| 会话状态 | START 的代码处理 |
|---|---|
| IDLE | 内部规范化为 UPDATE，允许无增量，建立默认基本信息草稿并询问缺口 |
| COLLECTING | 规范化为 REVIEW，继续当前草稿 |
| READY_TO_CONFIRM | 规范化为 REVIEW，展示当前确认单；不提交 |
| SUBMITTED | 展示已提交状态，并引导明确描述一张新申请；START 本身不创建第二张 |

NEW 继续表示明确另外新建；已有未完成草稿时继续按现有规则保留旧草稿并引导处理。

空 UPDATE 不自动转为 START，首先进入修复。START 中出现已知日期表达、城市候选或交通选项等明显事实信号时，也进入修复，检查是否遗漏。信号检测只用于发现可疑空结果，不依据关键词自动填字段或执行操作；它不能证明全部语义已经覆盖。

### 5.2 用稀疏申请训练输出行为

新增对照示例，至少覆盖：只有意图、意图加日期、只有地点、只有业务目的、短回答、否定提交、已有多段时目标不明。

基准日期为 2026-09-09 时，本次案例的正确增量包含：

```json
{
  "intent": "UPDATE",
  "submit_requested": "N",
  "basic_updates": [],
  "trip_operations": [
    {
      "op": "ADD",
      "trip_id": "NEW1",
      "after_id": "END",
      "kind": "MOVE",
      "evidence": "我明天要去出差了，帮我提个申请吧",
      "updates": [
        {"field": "depart_date", "op": "SET", "value": "2026-09-10"}
      ]
    }
  ],
  "clarification": "",
  "consultation": "",
  "clarification_resolutions": []
}
```

不为未知目的地写空字符串 SET，不编造具体业务目的，也不把“帮我提个申请”当作确认提交。

### 5.3 精简上下文，降低不必要的理解负担

N02 为模型单独生成草稿视图：保留草稿 ID、业务字段、行程稳定 ID、段类型、字段值及必要来源标记，如 USER_CLEAR。保留当前日期、可用候选、语义歧义、缺口和上一轮实际提问。

不把旧字段的原话证据、内部映射对象、交通推荐计算细节等继续作为 current_draft 全量传入。完整状态仍留给代码节点使用。N06 目前已经负责生成稳定行程 ID，本期保留这项能力。

Memory 继续关闭，以明确保存的草稿和提问目标提供上下文。日期本期仍按 N03 的业务时间上下文解析；将日期计算全面转入代码需要新的日期表达契约，列入第二阶段。

## 6. 一次自动修复的规则

### 6.1 N04 返回的业务状态

| status | 含义 | 后续 |
|---|---|---|
| OK | 结构及操作契约可执行；允许字段未填完整 | N05P |
| REPAIR | 有明确解析错误，可以重新理解原话 | R01 |
| CLARIFY | 无法通过再生成可靠确定目标，或输入超过支持范围 | R03 |

不将 Python 异常或会话损坏包装为 CLARIFY，执行异常进入 E99。

### 6.2 错误分类

| 情形 | 处理 |
|---|---|
| UPDATE/NEW 无增量且无澄清 | `EMPTY_UPDATE`，修复一次 |
| START 为空但原话含明显事实信号 | `POSSIBLE_FACT_OMISSION`，修复一次 |
| JSON 解析失败、键或类型不符、操作枚举冲突 | 修复一次，不猜测截断内容 |
| SET 空值、证据不属于本轮原话 | 修复一次；复检时继续严格检查 |
| 意图与修改矛盾、未知问题 ID | 修复一次，不跳过约束 |
| 多个修改目标均可能成立 | 澄清目标；不为降低报错率任选一段 |
| 普通缺字段、未知业务城市、路线不闭环 | 正常进入 N07 的补充或规则流程 |
| 无权限、行程重叠、未核对新版 | 保留业务拒绝，不要求模型“修到可以提交” |
| 会话状态损坏、校验服务失败 | 系统异常；不清空草稿、不当作通过 |

本期重点覆盖 N04 发现的契约错误。N06 发现的插入位置不存在、合并关系冲突等，仍保留其整轮回滚和针对性提示；不要宣称已把全部合并失败纳入自动修复。

JSON 错误修复适用于 N03 已完成、N04 实际取得输出的情况。若定制版在 N03 内部就因结构化输出解析失败而终止，N04 不会运行，本期沿用 E99。必须在现场用节点日志区分这两种情况，不能假定 N03 的失败出口还能提供 structured_output。

### 6.3 修复输入与模型配置

`repair_input_json` 包含：本轮原话、当前业务日期和时区、精简草稿、待回答问题、首次结构化输出或可取得的原始文本、error_code、error_path、约束说明。

R01 使用同一公司模型 `deepseek-V4-0731`、相同 Schema，Temperature=0、Top P=1、Max output tokens=8192；只发送供应商支持的参数。Memory 关闭。修复节点建议不另加调用重试，调用失败进入 R03，以限制失败场景的耗时。

修复指令要求重新理解原话，检查日期、地点、具体事由和修改目标；只能输出有依据的信息；空缺保持未知；无法判断时给出明确澄清，不以补默认业务事实满足 Schema。

首次与修复结果都必须通过同一套校验。交付时从同一校验实现生成 N04/R02 的独立节点代码，避免两套规则漂移；Dify Code 运行时不导入本地其他文件。

每轮最多一次**语义修复**。N03 原有调用失败重试与语义修复分别记录；不循环执行提交节点，不将修复次数直接当作网络调用次数。

### 6.4 两次都失败时

修复未通过或无法执行时，R02/R03 生成无业务增量的 CLARIFY 计划。计划保留当前原话、错误位置和恢复问题，失败输出中的城市、日期和操作不得进入有效草稿。

若能确定失败字段或目标，提问聚焦该处；只能知道解析整体失败时，明确提示“这轮内容还没有记录，请重新说明要补充或修改的内容”，并结合已保存草稿询问最关键的一到两个缺口。

保留 E01 文案作为最后保护，不再把内部错误码、Schema 或节点名直接展示给业务用户。

## 7. 对话状态与回复

### 7.1 状态版本

唯一会话变量继续为 `cv_session`，String，默认 `{}`。新版内部 `schema_version` 使用 `mvp1.2`。

在原有状态字段外新增 `dialogue`：

```json
{
  "focus": {
    "draft_id": "",
    "revision": 0,
    "questions": []
  },
  "recovery": {}
}
```

focus.questions 最多保存本轮展示的两个问题，每项包含问题 ID、目标行程、字段和问题文本。全部缺口仍保存在 pending；当前只问两个，不表示其余问题被解决。

recovery 非空时保存：由代码分配的恢复问题 ID、失败消息、该消息的业务日期、错误码及路径、基础草稿 ID/版本、恢复问题和可确定的目标字段。失败消息仅作诊断与提醒，**本期不授权模型把旧失败消息作为新一轮写字段的证据**。N02 向模型只提供恢复问题的 ID、目标和问题文本，不传旧失败消息原文。

恢复问题 ID 使用 `Q-RECOVERY-` 前缀，并以 CLARIFICATION 问题同步到 pending。N03 沿用 clarification_resolutions 表达本轮回答了该问题；N04/R02 对照恢复目标和本轮证据校验，N06 仅在实际合并成功后解除候选 dialogue.recovery。N07 从 candidate_json 读取候选 dialogue，将仍存在的恢复事项列入 issues；N09 保存同一份候选 dialogue，防止提前解除。

只有可以可靠定位的稳定行程和字段才登记为恢复目标。若目标未知、后来被删除或含义已变化，按整轮恢复处理，不能根据旧数组位置猜测目标。对于整轮恢复，本期只接受本轮包含有效更新且用户以独立肯定分句明确说“上次未记录的内容以这次为准”，或独立指令“忽略上次未记录内容”；代码检查原话中的明确声明，不接受否定、询问、引用或假设。暂不能可靠识别的表达继续澄清，不由模型自行授权忽略。

每次新的失败都须保留此前尚未解决的恢复事项；本期只保留一个完整失败消息、最近三条错误摘要及累计失败次数，后续失败将目标提升为整轮恢复，不覆盖已有问题后声称旧问题已解决。完整诊断仍以 Dify 逐轮日志为准。

旧 `mvp1.0` 状态只做结构校验后的加字段迁移，不清空草稿、历史或已提交记录。若存在未完成草稿，迁移后要求重新展示一次确认单；已提交记录及指纹保持原值，用于重复提交识别。未知或损坏版本进入 E99。

### 7.2 恢复事项的生命周期

- 正常首次解析或同轮修复成功：保存有效草稿，按真实缺口追问。
- 两次失败：保存恢复事项；有效草稿不采用失败候选值。已有未提交草稿时清除旧确认状态，阻止直接提交旧版本。
- 恢复事项有明确目标：用户本轮重新提供该目标的有效值，并通过目标及证据检查后，才可解除。无关修改可以记录，但不能顺便解除恢复事项。
- 目标未知或涉及整轮未应用内容：用户需重新说明并明确以新内容为准，或单独回复“忽略上次未记录内容”。该指令只撤销未应用的恢复事项，不取消整张草稿。
- “忽略上次未记录内容”由代码根据当前原话判断；模型不能自行决定忽略。解除后重新校验并展示确认单，不能直接提交。
- 整单取消同时清理恢复事项；已生成的模拟单据历史继续保留。
- 已提交状态发生新一轮解析失败，不修改已提交结果；待用户明确新申请意图后再创建草稿。

本期不实现“删掉出错字段后执行其余操作”的通用部分提交。现有整轮合并回滚继续保留；完整、合格的稀疏增量可以正常保存。

### 7.3 回复策略

| 阶段 | 展示内容 |
|---|---|
| 开始申请 | 简短说明已开始填写，问出发日期和目的地 |
| 收集中 | 已记录/已修改的关键内容，下一到两个问题 |
| 需要澄清 | 明确哪一项尚未确定，给出可区分的候选目标 |
| 完整待确认 | 完整确认单、默认及建议来源、明确的确认提交提示 |
| 用户要求查看 | 完整当前草稿及全部待处理项 |
| 模拟提交结果 | 沿用现有结果与模拟边界说明 |

优先处理语义歧义和规则冲突，再补决定路线的日期/目的地、具体事由和返程；交通建议等待起止城市确定，避免目的地未知时先要求选择交通。

回复由代码按真实状态生成，本期不增加专门润色回复的 LLM。N13 成功保存后由 N14 展示；不对 N13/N14 的错误沿用“尚未写回”的承诺。

### 9.2 真实模型验收

先使用 20 条重点表达、每条在固定前置状态下独立运行 3 次，MVP1.1/MVP1.2 各 60 次。通过后扩大到 60 条表达、每条 5 次，各 300 次，再补充 10 组多轮脚本、每组 3 个新会话。

表达覆盖稀疏信息、普通填写、修改与否定、插入咨询、复杂行程和歧义。保留未写进 Prompt 的变体作为验收用例，避免只测提示词里的例句。评判日期、城市、事由、目标行程和是否正确保存，不要求回复逐字一致。

两版保持同一模型、模型参数、测试日期、身份场景和前置草稿。分别记录自动修复与用户重新发送；用户手工重发成功不能记成首遍成功。

| 指标 | 统计口径 |
|---|---|
| 首遍语义正确率 | 首次结果正确提取应有事实、未错改旧事实的消息数 / 总消息数 |
| 自动修复触发率 | 进入 R01 的消息数 / 总消息数 |
| 修复成功率 | R01 后语义与操作均正确的消息数 / 进入 R01 的消息数 |
| 修复后消息正确率 | 首次或一次修复后正确完成本轮操作的消息数 / 总消息数 |
| 用户恢复提问率 | 进入恢复提问的消息数 / 总消息数；区分自然歧义和系统解析失败 |
| 完整会话完成率 | 正确记录全部要求并达到预期结束状态的会话数 / 可完成的测试会话数 |
| 无依据写入与错误提交 | 分别统计错误字段、丢失修改和不应发生的创建 |
| 耗时与调用成本 | 分正常、自动修复、系统失败统计 P50/P95、实际调用次数和 token |

建议首轮验收目标：300 条固定基准中，修复后语义正确率至少 98%；自然歧义应正确追问；错误提交、草稿被意外清空为 0 次；正常路径 P95 耗时不超过同批 MVP1.1 的 1.2 倍。模型调用错误单列，同时计入端到端失败。上述是拟定验收目标，不是当前结果或生产保证。

修复后结构合法但仍遗漏业务事实，必须记为失败。若失败集中在复杂行程定位，而非格式和空增量，应进入第二阶段的语义结构调整，而不是继续增加修复次数。

## 10. 第二阶段与 Agent 的适用位置

| 后续改造 | 启动依据 | 设计要求 |
|---|---|---|
| 事实提取与操作规划分离 | 复杂改动、行程归属错误集中出现 | 提取原话事实和目标线索，再结合草稿生成内部操作；用真实对照集评估额外调用是否有收益 |
| 日期规范化模块 | 相对日期计算错误集中出现 | 定义日期原文、锚点、时区及归属；代码计算明确表达，歧义继续提问 |
| 跨轮恢复失败消息 | 二次解析失败后反复要求用户重述 | 引入消息 ID、该消息业务日期和受限证据来源；防止旧“明天”漂移和旧修改重复执行 |
| 局部 Agent | 需要动态查询政策、活动或多来源候选 | 限定工具及最大迭代；工具结果回到现有代码校验，再合并草稿 |

本期不将 N03 直接替换为 Agent。Agent 的价值在于根据中间结果决定下一次工具调用；若需求只是把空增量重新提取一次，显式修复分支已经可以提供这项能力。

若后续试用 Agent，先比较它在政策或活动查询中的收益；真实提交仍由受控流程依据当前草稿、确认版本和业务校验执行。
