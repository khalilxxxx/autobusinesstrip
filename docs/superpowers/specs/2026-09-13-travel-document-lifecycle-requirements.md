# 差旅单据生命周期扩展需求分析

日期：2026-09-13。版本：V0.5，明确 S005 变更作废、查询范围及用户指定的执行约束。

本稿依据用户关于查询、撤回、作废、连续行程变更的说明，以及后续确认整理。沿用已确认的最新规则：行程变更提交、撤回、编辑重提和审批完成时，原单 tflag 均为 YBG，新变更 tflag 均为 D；审批完成前原单仍有效，完成后新变更生效。S005 可沿原单号和连续审批流编辑重提，也可通过 AI 助手作废该变更，变更单变为 S100/D、原单恢复 D 并继续有效，之后允许重新发起变更。已完成单据只允许作废当前有效版本，不恢复被替代旧版。作废无需额外审批，成功即 S100；已被替代版本不向员工提供查询。报销相关流程不在本次范围；变更允许修改事由、差旅类型、部门及付款公司。实施时先 Git 保存旧版，再开发新版；Dify 必须新建独立应用并保留当前工作流。

文中分别标注已明确规则、建议方案和待明确口径；建议方案尚不等于已确认制度。本文用于需求评审，验收场景均为待执行设计。

## 2. 已明确的规则与需要分开的概念

### 2.1 审批状态

| 状态 | 含义 | 本轮明确的处理 |
|---|---|---|
| S001 | 草稿 | 尚未正式提交 |
| S002 | 已提交 | 本次提交/重提后尚未发生人员审批；支持撤回 |
| S003 | 审批中 | 本次提交/重提后已有任一人员审批；不支持员工撤回 |
| S004 | 已完成 | 单据审批完成；当前有效且未转报销时属于作废、行程变更的基础适用范围 |
| S005 | 撤回或退回 | 允许编辑重提，沿用原单号，审批流连续；若是行程变更单，还允许作废 |
| S100 | 已作废 | 可由符合条件的 S004 有效单据或 S005 行程变更单作废后进入，二者影响分别见第 6 节 |

S002 的撤回资格取决于当前审批状态和审批事实，不设用户未提出的“提交后若干分钟内”限制。主管打开页面、收到待办，不自动等于已发生审批；具体以业务系统的状态和办理记录为准。

用户明确的连续流转示例为 `S001 → S002 → S003 → S005 → S002 → S003 → S004`。同一单据可以多次编辑、重提和继续审批，单号与已有审批历史保留。重提回到 S002 时，撤回资格应检查本次提交后的审批事实，不能因早前存在 S003 的历史记录就判为不可撤回。提交轮次用于区分办理记录，不代表重新建立一条无历史的审批流程。

S004 表示审批完成，不能据此推断出差已经结束。未来行程也可能已获批进入 S004；历史日期的申请也可能仍在审批或处于 S005。

### 2.2 转报销标识

| tflag | 用户给定含义 | 分析结论 |
|---|---|---|
| D | 待报销；新变更从提交起，在撤回、编辑重提及审批完成时均为 D | 不代表已经审批完成或已经生效，需结合审批状态和版本关系 |
| YBX | 已经转报销 | 不支持本轮作废和行程变更；不等同于报销审批或付款已完成 |
| YBG | 已提交后续行程变更；后续变更撤回、编辑重提及完成时，前序单据均保持 YBG | 不代表前序单据已经失效；后续变更完成前前序仍有效 |

“未转报销”不能直接等同于 `tflag=D`，因为 YBG 也不是 YBX。原单在变更待审批期间为 `S004 + YBG`，仍然有效；新变更虽为 D，也可能处于 S002、S003 或 S005。因此不能仅凭 tflag 判断审批阶段、当前有效版本或操作资格，必须检查变更关系和流程状态。

用户已明确：A1 提交、撤回、编辑重提和审批完成时，均为 A=YBG、A1=D。A1 在 S005 被作废时，A 恢复 D，A1 为 S100/D，A 继续有效。A1 正常完成后可以作为 A2 的前序单继续变更；A2 提交时对应 A1=YBG、A2=D，根单 A 保留原有标识与后台历史。详见第 7.3 节。

### 2.3 单据类型、版本效力和行程时间

| 维度 | 回答的问题 | 示例 |
|---|---|---|
| 单据类型 | 这是什么单据 | 差旅申请、行程变更 |
| 审批状态 | 审批进行到哪一步 | S002、S004、S005 |
| 转报销标识 | 当前 tflag 值及其业务含义 | D、YBX、YBG；变更进度与版本效力需另查关联流程 |
| 版本效力 | 哪一张当前代表已批准安排 | 待生效、当前有效、已被替代、已作废 |
| 行程时间 | 出差日期与查询时间是什么关系 | 历史、当前、未来 |

版本效力是本稿建议增加的业务表达，并非已知的公司系统枚举。作废的正式状态已明确为 S100；S005 表示可编辑重提的撤回/退回，S100 表示已作废，二者分别处理。

### 2.4 已确认的串行变更

用户已明确：不允许并行变更。A 审批完成后可发起 A1；A1 审批完成后，才能基于 A1 发起 A2；后续依此类推，变更次数不限。

发起新变更的基础是当前有效且满足条件的已完成版本：A1 仍在途时，不能基于 A 创建另一张并行变更；A1 生效后，下一张必须基于 A1。若 A1 在 S005 被作废，A 一直有效，允许重新基于 A 发起新的变更，该新变更的前序不能指向已作废的 A1。

本文“在途变更”指已经提交、尚未完成且尚未作废的变更，包含 S002、S003，以及仍能沿原流程重提的 S005。同一有效前序最多关联一张在途变更；S005 时可以编辑重提原单，也可以先作废该变更再重新发起。已作废变更保留后台记录，不能再重提或生效。同一前序可以留下多次已作废尝试，但同一时刻只能有一张在途变更；不能把串行约束实现为“同一前序一生只能创建一张变更”。仅在助手中编辑、尚未提交的本地草稿不视为已建立在途审批流程。

## 3. 总体业务模型与操作矩阵

建议采用“独立关联单据 + 当前有效版本”的方式：后台保留 A、A1、A2 各自的内容、审批过程和单号，同时记录原始申请、直接前序和当前有效版本。审批完成时切换有效版本；员工查询过滤已被替代的旧版本，后台记录用于关系判断和核对。

| 方案 | 特点 | 评估 |
|---|---|---|
| 覆盖原单内容 | 单据数量少，但需另补快照才能保留原审批依据和待审批修改 | 单纯覆盖不满足原单继续有效及历史追溯要求 |
| 独立关联单据 + 当前有效版本 | 保留每次变更，能明确呈现串行关系和生效切换 | 推荐，与已给定业务最一致 |
| 全量事件重建状态 | 能重建每次历史变化，但建设和查询成本较高 | 当前可以先保留必要操作记录与生效时间，无须扩大系统范围 |

以下矩阵用于定义目标操作资格。查询均以具有相应查看权限为前提；作废还取决于第 6 节的作废范围及后续流程规则。

| 单据情况 | 查询 | 撤回 | 作废 | 发起下一次行程变更 |
|---|---|---|---|---|
| S001 草稿 | 可查草稿 | 不适用 | 不适用 | 不适用，直接修改草稿 |
| S002，本次提交后尚无人审批 | 可查，标注待审批 | 支持，成功后 S005 | 不支持 | 不支持 |
| S003 | 可查，标注审批中 | 不支持 | 不支持 | 不支持 |
| S004，当前有效，D，无在途变更 | 支持 | 不支持 | 支持基础条件成立 | 支持 |
| S004，YBX | 支持 | 不支持 | 不支持 | 不支持 |
| S004，YBG，仍有效，但已有 S002/S003 变更 | 支持，并展示变更 | 不支持撤回原单 | 不支持直接作废，先将变更处理至 S005 并作废 | 不支持并行变更 |
| S004，YBG，关联变更为 S005 | 支持，并展示可重提变更 | 不支持撤回原单 | 先作废 S005 变更，再判断原单 | 可重提原变更；或作废后重新基于原单发起 |
| S004，已被后续变更替代 | 不向员工提供旧版查询 | 不支持 | 不支持 | 不支持，应定位当前有效版本 |
| S005 普通差旅申请 | 支持，展示产生该状态的动作 | 不适用 | 不支持；本轮新增规则仅适用于 S005 变更单 | 支持原单编辑重提，不是新一代变更 |
| S005 行程变更单，D | 支持 | 不适用 | 支持，成功后变更 S100/D、前序恢复 D 并持续有效 | 可编辑重提同一变更；作废后可基于前序重新发起 |
| S100 已作废 | 支持未被替代的作废记录，标注已作废 | 不支持 | 不重复执行 | 本单不能重提或作为变更前序；有效原单可另起变更 |

建议将上述判断集中由业务服务完成，并返回可执行操作及不可执行原因。聊天回复、详情卡片、表单入口必须遵循同一结果，执行时再次核验。

## 4. 查询单据需求

### 4.1 两类查询目标

“查一下上个月的申请”“看看 A1 审批到哪一步”属于单据查询：查询允许展示的单据及状态，待审批、S005、已作废记录明确标识；已被后续变更替代的旧版本不向员工展示。

“下周在哪里出差”“9 月 10 日去上海对应哪张申请”属于行程查询：根据行程日期、地点和版本关系，找到对应申请及有效变更。建议优先回答已批准的有效安排，另列匹配的待审批计划，避免把待审批安排说成已生效。

查询范围应覆盖业务系统中有权限查看的单据，包括通过其他入口创建的单据。聊天记录只提供指代线索，不能代替单据数据源；删除会话不删除单据及审批历史。

### 4.2 查询条件与时间口径

| 用户表达 | 建议解析与查询方式 |
|---|---|
| “查我的历史/当前/未来差旅” | 以行程日期分类；不使用创建日期或 S004 代替 |
| “上个月提交的单据” | 明确按提交时间筛选 |
| “上个月出差的单据” | 按行程与上个月的时间交集筛选 |
| “查 9 月 10 日在哪里出差” | 查询覆盖该日期的行程与中间停留，再定位有效版本及原始申请 |
| “查去上海的申请” | 匹配目的地和停留；必要时区分途经上海与以上海为目的地 |
| “看看刚才那张/第二张” | 解析到当前结果集中的确定单据；没有唯一对象时展示候选 |
| “查 A 的变更” | 展示当前有效单据及在途变更；不展开已被替代版本的历史列表 |

建议明确使用业务时区，当前 Demo 为 Asia/Shanghai。相对日期应展示解析后的绝对日期；只有“9 月”而没有年份，且存在多个合理年份时，应先消除歧义。

建议以闭区间解释日期粒度的查询。行程范围 `[start, end]` 与查询范围 `[qStart, qEnd]` 满足 `start <= qEnd 且 end >= qStart` 即有交集。这样可覆盖跨月、跨年或只部分落在查询区间的出差。该口径只用于查找，不自动新增历史行程冲突规则。

按今天分类时，建议：`end < 今天` 为历史；`start <= 今天 <= end` 为当前；`start > 今天` 为未来。日期分类仅说明申报安排处于哪个时间段，不代表已经实际出行。

### 4.3 “某天在哪里”的关键边界

现有单段的到达日期是到达目的地的日期，不是停留结束日期。假设 9 月 10 日杭州到上海、9 月 13 日上海到北京、9 月 15 日北京回杭州，则 9 月 11 日的申报安排是在上海。仅查询“出发日或到达日等于 9 月 11 日”的交通段会漏查。

建议利用相邻行程间的日期和衔接城市推导停留，并说明来源于申报行程。9 月 13 日只有日期、没有时分时，应表达为“当天有上海到北京的行程”，不能断言全天在某一个城市。日期不连续、城市不衔接、数据不足或多个行程互相重叠时，展示已知安排和不确定部分。

助手能回答的是“按单据记录/已批准行程，当时或预计的出差安排”。没有实际履约或定位数据时，不能证明员工实际到过某地。

### 4.4 历史差旅与被替代版本的查询边界

已确认：已被新变更替代的旧版本不向员工提供查询。默认按当前有效版本回答出差安排，在途变更另行展示。A1 获批替代 A 后，员工列表和详情不再返回 A 的旧版内容；若输入旧单号 A，可提示对应的当前有效单据为 A1，并展示 A1，不提供旧版本详情入口。

“历史差旅”按出差日期理解，仍在本次查询范围；“历史版本”指已被后续有效变更替代的旧单，已明确从员工查询中排除。例如上个月的一次出差，仍可按该次差旅的当前有效单据查询。后台保留前后关系和办理记录，但不建设员工历史版本浏览、对比或按过去时刻还原旧版的入口。

同一变更链在汇总有效行程时只计一次。按城市、时间查行程时，先选择应展示的有效版本，再匹配其行程内容，避免用旧版城市命中新版已经变更的路线。S005 变更被作废后，原单仍有效并继续参与查询；已完成的当前有效单被作废后，不用其被替代旧版补充有效安排。作废记录不作为有效行程回答，查不到有效安排也不等于从未申请过。

### 4.5 结果展示与异常

列表建议展示单号、单据类型、申请人、主要城市、出差日期、事由、审批状态、转报销情况和版本效力，支持分页及继续缩小条件。详情展示完整路线、原始申请号、当前有效单号、在途变更和关键审批时间；原始申请号可用于关联说明，不开放被替代原单的详情。S005 另展示撤回/退回类型、时间及已有原因。

无匹配记录、无权访问、查询失败三种结果应分别处理。多条匹配时提供候选，不能随意选择一张执行后续操作。显式指定状态也只返回符合员工查询范围的记录；不能借此绕过被替代版本的隐藏规则。

## 5. 撤回单据需求

已明确：员工只能撤回 S002、本次提交后尚未开始实际审批的单据；撤回成功后为 S005。S003 与 S004 不支持本项撤回。

建议流程为：定位目标单据 → 获取最新详情和资格 → 向员工说明目标及结果 → 执行撤回 → 返回 S005 及业务回执。明确的操作按钮或已明确目标与动作的自然语言可以作为操作表达；信息不足时补齐对象，避免固定叠加多轮重复确认。具体授权方式应与现有提交交互保持一致。

撤回后保留原单号、内容和审批记录，并记录操作类型为“员工撤回”。审批人退回也进入 S005，但应显示“审批退回”、办理人及已有退回原因，不能把它展示为员工主动撤回。

用户已明确变更撤回场景，同样的 S002 撤回能力适用于行程变更单。例如 A1 被撤回后为 S005、tflag=D，A 的内容和 tflag=YBG 保持，继续有效；撤回 A1 不等于作废 A 或取消整趟差旅。

已明确：S005 允许编辑重提，沿用原单号，重提后回到 S002 并沿连续审批流办理。已有撤回、退回、审批记录和各次提交内容需要可追溯，不能将流程历史清空或把编辑重提生成一张新单。A1 在 S005 修改后重提仍然是 A1，只有 A1 完成后再发起新的行程变更才形成 A2。

若重提的是 A1，需重新核验前序 A 仍有效且未作废，以及没有其他在途变更，防止基于过期单据重提。相同网络请求重试沿用原请求号；员工编辑完成后主动发起的新一轮重提使用新的操作请求号，同时保持单据身份、单号及连续审批历史。

S005 是连续审批中的可编辑重提状态。用户已进一步明确：要结束该变更，就通过 AI 助手作废 S005 变更单，使其进入 S100，并将原单 tflag 恢复 D。仅撤回到 S005 还没有完成这一步；S005 可以继续重提，S100 不再允许重提。

本期撤回、作废和行程变更均不设必填操作原因。用户已表达的原因可随操作保留，不因缺少原因额外追问或阻止办理；申请单原有事由按既有规则保留或修改。

撤回操作必须在业务服务中原子校验：员工打开确认界面时是 S002，但执行时已进入 S003，应拒绝撤回并更新状态；不得把 S003 强行改成 S005。

## 6. 作废单据需求

最新确认的作废规则分为两类：

| 作废类型 | 前置条件 | 成功结果 | 对原单/前序的影响 |
|---|---|---|---|
| 作废已完成单据 | 当前有效的 S004，未转报销，且没有在途变更 | 被操作单据进入 S100 | 不恢复已被替代的旧版，该次差旅不再有有效安排 |
| 作废尚未完成的行程变更 | 单据类型为行程变更，当前 S005 | 变更单进入 S100、tflag=D | 直接前序的 tflag 恢复 D，前序继续有效，允许重新基于它发起变更 |

第二类是用户对原先“仅 S004 可作废”的明确补充，只适用于 S005 行程变更单。S005 普通差旅申请不因此获得作废能力；S001、S002、S003 不能直接作废，YBX 仍不适用。两类作废均可通过 AI 助手办理，无需额外审批，成功即 S100；本期不设必填作废原因。

已完成单据仅允许作废当前有效版本；已被替代的 A 不能单独作废，也不提供员工查询。操作前展示目标单号、行程和影响，区分作废未生效变更、作废当前有效申请、删除某段行程或取消当前编辑。

原单 A 已提交变更 A1、但 A1 尚未完成时，A 仍有效且为 `S004 + YBG`，A1 的 tflag=D。此时不能直接作废 A，应先结束 A1：若 A1 为 S002，可撤回至 S005 后作废；若 A1 已是 S005，可直接作废；若 A1 是 S003，员工不能撤回或直接作废，需在现有审批流程中退回至 S005 后办理。AI 助手不代替审批人执行审批退回；Demo 可在模拟控制台推进退回状态。

A1 作废成功后为 S100/D，A 为 S004/D 且继续有效。员工可以保留 A 并重新发起新的变更，也可以在重新核验 A 满足条件后作废 A。前置动作与最终动作分别保留回执；只作废 A1 不等于已经作废 A。

用户已明确：作废已完成的当前有效 A2 后，不允许自动或手动恢复此前被替代的 A、A1；后台保留记录，员工不查询这些旧版本。与此不同，作废 S005 的 A1 时，A 从未被 A1 替代过，继续有效属于保留现状。两条规则分别覆盖“取消未生效变更”和“作废已生效版本”。

作废结果未知时先查回执，不重复发起。作废是保留记录的业务操作，不能通过删除数据库记录、草稿或聊天会话实现。转报销相关流程及并发规则已按用户要求移出本次分析范围。

## 7. 行程变更需求

### 7.1 基本流程

1. **找到基础单据。** 根据单号、时间地点或会话上下文定位，并核验它是否是当前有效、S004、未转报销且没有在途变更的版本。命中旧版本时说明有效版本并定位，不能基于旧版本建立分支。
2. **继承并编辑。** 复制已批准版本的内容形成变更草稿。保留未修改字段及原始申请关系，支持自然语言和结构化表单编辑。
3. **展示差异。** 同时呈现变更前后及完整变更后行程，例如返程由 9 月 15 日改为 9 月 17 日。说明变更审批完成前原安排继续有效。
4. **校验并提交。** 沿用完整性、日期顺序、路线衔接、闭环、交通与城市规则；按最终核对内容提交独立行程变更单，进入 S002。
5. **跟踪审批。** S002、S003 阶段原已批准版本持续有效。助手展示审批中安排与有效安排，明确两者关系。
6. **切换生效。** 变更审批完成进入 S004 后，以新版本为准；前序版本保留为历史。
7. **继续变更。** 后续只能基于新获批版本开始下一轮，无业务次数上限。

变更支持出发/到达日期、城市、交通、增加或删除行程段；用户已确认同时允许修改事由、差旅类型、部门及付款公司。删除一段后仍需满足整单规则；未修改内容原样继承，不能以员工默认值覆盖原单。非行程字段的修改也进入变更前后对照和审批内容，并在变更完成后随新版本生效。

变更编辑需要提供部门、付款公司及差旅类型的可选信息，支持自然语言与表单两种方式修改。当前 Demo 原有固定部门/公司不能代表已覆盖这项能力，后续演示需提供明确的模拟候选；正式系统沿用原有可选范围和校验，不因允许修改而扩大员工权限。

若日期调整涉及相邻段，应展示受影响内容；缺少新的日期或交通时补问，不能为了通过校验编造事实。现有历史日期支持仍保留；是否有额外的“行程结束后不得变更”等制度，本轮没有提出，不新增限制。

### 7.2 连续变更示例

| 业务阶段 | 原单/前序状态 | 新变更状态 | 当前有效安排 | 下一步约束 |
|---|---|---|---|---|
| A 已获批 | A：S004 | 无 | A | 未转报销等条件满足时可发起 A1 |
| 编辑 A1 草稿 | A：S004 | 草稿；仅本地编辑时不擅自称为系统 S001 | A | 草稿不触发替代 |
| A1 提交 | A：S004 | A1：S002 | A | 不可并行发起另一张变更；不可直接作废 A |
| A1 已有人审批 | A：S004 | A1：S003 | A | A1 不可员工撤回 |
| A1 被撤回/退回 | A：S004 | A1：S005 | A | 可编辑重提 A1，或通过助手作废 A1 |
| A1 编辑后重提 | A：S004 | A1：S002，原单号及审批历史保留 | A | 沿连续审批流处理，不生成 A2 |
| A1 在 S005 被作废 | A：S004，tflag=D | A1：S100，tflag=D | A | 可重新基于 A 发起新变更；A1 不再重提 |
| A1 审批完成 | A：S004，已被替代 | A1：S004 | A1 | 条件满足时可基于 A1 发起 A2 |
| A2 提交并审批中 | A、A1 保留各自审批历史 | A2：S002/S003 | A1 | 不可并行发起 A3；不可直接作废 A1 |
| A2 审批完成 | A1：S004，已被替代 | A2：S004 | A2 | 条件满足时可继续 A3，无次数上限 |

旧版本的 S004 可以保留，因为它的审批确实完成过。它是否仍有效，由版本关系表达；不能把所有 S004 同时当作当前有效行程，也不能仅按单据创建时间选择“最新一张”作为有效版本。

### 7.3 已确认的 tflag 与流程联动

以下取值以用户最新给出的流转规则为准。表中的“原单”始终指新变更的直接前序；A2 的原单是 A1，不能每次都更新根单 A。报销相关变化不在本表范围内。

| 事件 | 原单状态/tflag | 新变更状态/tflag | 当前有效版本 |
|---|---|---|---|
| A1 成功提交 | A：S004 / YBG | A1：S002 / D | A |
| A1 审批中 | A：S004 / YBG | A1：S003 / D | A |
| A1 撤回/退回 | A：S004 / YBG | A1：S005 / D | A |
| A1 编辑后重提 | A：S004 / YBG | 同一张 A1：S002 / D | A |
| A1 审批完成 | A：S004 / YBG | A1：S004 / D | A1 |
| A1 在 S005 被作废 | A：S004 / D | A1：S100 / D | A |
| A2 成功提交 | A1：S004 / YBG | A2：S002 / D | A1 |
| A2 撤回/退回 | A1：S004 / YBG | A2：S005 / D | A1 |
| A2 审批完成 | A1：S004 / YBG | A2：S004 / D | A2 |
| A2 在 S005 被作废 | A1：S004 / D | A2：S100 / D | A1 |

仅编辑本地草稿时，前序 tflag 不变；本地草稿未成为系统单据时不声称已写入业务系统。作废 S005 变更的返回值和关联更新已明确，不再需要另设业务“终止”状态。作废后重新发起变更要生成新单，不能将 S100 的旧变更改回 S002；新单提交时，再把当前有效前序设为 YBG、新单设为 D。

由该表可直接得到三个约束：原单 YBG 不代表已经失效；新变更 D 不代表已经审批完成或生效；审批完成时即使双方 tflag 没有变化，仍必须切换当前有效版本。在途关系、作废结果及当前有效版本应独立记录，不能把 tflag 变化作为版本生效的触发条件。作废 S005 变更时，需同步解除在途关系并把其直接前序恢复 D，不能误更新更早的根单。

### 7.4 生效一致性与本次范围

建议一条仍有效的变更链在任一时刻只有一个当前有效版本；首张申请尚未获批时可以没有，整条行程作废后也可以没有。只有合法前序的当前变更审批完成才能切换，新旧状态和有效版本关系应保持一致。

用户已明确：实际业务允许变更审批期间原单转报销；本次需求不涉及报销相关内容。因此本稿不设计转报销操作、冻结、锁定、同步流程或与变更的竞态处理，也不将其作为本轮开发/验收前置条件。

保留用户最初给定的本轮操作条件：已是 YBX 的单据不支持发起作废或新的行程变更。读取已有 tflag 用于这些条件及详情展示即可，不能由此扩展为报销功能建设。

## 8. 助手交互与上下文需求

| 用户表达/场景 | 应识别的需求与处理 |
|---|---|
| “查下周的差旅单” | 只查询，按出差时间找单并展示状态 |
| “把刚提交那张撤回” | 定位提交结果对应单据，核验 S002 后处理撤回 |
| “把这趟出差取消掉” | 识别取消整单还是某一段；结合状态说明可采用撤回或作废，不能擅自替换成不同业务动作 |
| “已批的上海出差延后两天” | 定位当前有效单，形成行程变更草稿，展示所有受影响日期 |
| “A1 已通过，再改一次” | 以 A1 为基础发起 A2 |
| “把退回的 A1 改一下重新交” | 编辑并重提同一张 A1，保持原单号和审批历史 |
| “A1 已撤回，作废 A” | 说明并执行已明确的目标流程：先作废 S005 的 A1，再核验和作废 A，分别展示结果 |
| “A1 不要了，保留 A” | 仅作废 S005 的 A1；A 恢复 D 并继续有效 |
| “把付款公司和事由一起改掉” | 纳入行程变更内容及前后对照，随新版本获批后生效 |
| “不撤回了”“能撤回吗”“如果撤回会怎样” | 分别是取消操作、咨询资格、询问后果，均不能误触发撤回 |
| “撤销刚才的日期修改” | 撤销当前草稿编辑，不能误判成撤回已提交单据 |
| “看看去年那张”，当前正编辑新申请 | 保留现有草稿；查询结果和编辑对象分别记录 |
| 结果列表有两张上海申请，用户说“就这张” | 对象不唯一时先定位；不能自行取最近一张操作 |

建议在产品中使用中文动作名称，例如“查看详情”“撤回单据”“作废单据”“发起行程变更”“提交变更”。S005 变更单显示“编辑并重新提交”和“作废变更”；S005 普通申请仅提供适用的编辑重提操作。S100 不提供重提；被替代版本不提供员工查询、操作或恢复入口。

状态变化后，旧卡片中的操作资格会过期。打开详情或执行动作前刷新资格；来自不同会话的操作也应作用于同一权威单据状态。单据 ID、草稿编辑版本和变更链中的 A/A1/A2 业务版本分别管理。

用户已明确目标和动作时，应复用一次有效的操作表达；目标、差异或影响尚未展示清楚时，先形成可核对的操作摘要。查询不需要写操作确认，选择候选本身也不能被误当成任意其他操作的授权。

建议完成后的回复明确结果和影响：

- 撤回：“A1 已撤回，状态为 S005。原申请 A 继续有效。”
- 重提：“A1 已重新提交，状态为 S002，沿原审批流程继续办理；原申请 A 继续有效。”
- 变更提交：“变更 A2 已提交，等待审批。目前仍以 A1 的已批准行程为准。”
- 变更获批查询：“A2 已审批完成，当前以 A2 为准；A1 已被替代。”
- 作废 S005 变更：“A1 已作废，状态为 S100。原申请 A 继续有效，可以重新发起变更。”仅在取得实际成功回执后使用。
- 作废已完成单据：“A2 已作废，状态为 S100，该次差旅不再有有效安排。”仅在取得实际成功回执后使用。

能力上需要：单据条件查询、当前详情及后台关联解析、最新操作资格、撤回、两类作废、变更草稿/提交、S005 原单编辑重提、操作结果查询，以及审批/退回结果获取。S005 变更作废由 AI 助手调用对应作废能力完成，服务端同步更新前序和在途关系。本次不增加独立“终止”业务动作、历史版本查询或报销流程。

S001 的正式单据草稿和助手本地编辑草稿需要区分。不能因为用户尚未提交，就声称公司系统中已经存在一张 S001 单据。S005 单据回到助手编辑时也不能仅因编辑而把业务状态覆盖为 S001。

正式查询及写操作需要按当前员工身份校验单据权限，不能信任用户在对话中输入的申请人 ID。建议本期 Demo 延续固定演示员工；他人代办、主管代操作和批量撤回/作废未被本轮要求，不自动扩入实施范围。

现有样本缺少本轮状态字段，不能在后续迁移时把所有“创建成功”记录直接认定为 S004。Demo 宜提供具有明确状态和关联关系的样例；正式历史数据以公司系统为依据。

## 10. 异常及一致性要求

| 风险场景 | 需求结果 |
|---|---|
| 撤回与本次提交后的首个审批动作同时发生 | 在权威服务原子判断；本次审批已发生则撤回失败，不以早前轮次的审批记录误判 |
| 两个会话同时基于 A 发起变更 | 最多一张成功进入在途流程；另一张说明已有变更及其单号 |
| 作废与变更提交同时发生 | 不得同时产生“原单已作废”和“以它为有效基础的待审批变更” |
| S005 变更重提与作废同时发生 | 作废成功后不能重提；重提已成功进入 S002 时，过期 S005 作废操作应被拒绝 |
| 审批完成通知重复或乱序 | 不重复切换、不回退有效版本，不让已作废/过期变更重新生效 |
| 网络超时、服务重启、结果未知 | 保留原请求标识查询回执；未查到记录不等于明确失败 |
| 连续点击或原请求重传 | 同一操作返回同一结果；新一轮合法编辑重提有新请求号，仍沿用原单号 |
| 旧 S005 变更重提时前序已被替代 | 拒绝直接重提，说明当前有效版本；不能覆盖已经获批的新版本 |

操作记录应足以追溯“谁在何时对哪张单据做了什么，操作前后状态和结果是什么”。本轮无需建设通用审计平台，但要保留这些生命周期事实。
